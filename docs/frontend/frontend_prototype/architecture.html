Architecture rules

SOLID, high cohesion, low coupling

Implementation boundary

One reason to change, one clear owner

This prototype is documented as a composition of shell, design-system, feature, data, and transport boundaries. The UI can evolve without turning one domain into a dependency of another.

Dependency direction

Design system primitives ↑ Feature presentation components ↑ Feature route/view models ↑ Typed API/query adapters ↑ Tenant-aware transport

Composition root

The app shell owns navigation, tenant context, responsive drawer state, theme, density, notifications, and route outlet composition. It does not fetch domain records or implement task, finance, inventory, or agent rules.

Allowed: route metadata, typed view models, semantic callbacks.
Forbidden: sibling-store imports, direct fetch in presentational components, hidden authorization assumptions.

SRP

Each component has one reason to change: navigation, task row, metric card, assistant plan, or transport adapter.

OCP

New modules are added through route and navigation metadata plus feature components, not branches spread across the shell.

LSP

Loading, empty, forbidden, error, and ready states honor the same feature boundary and accessible contract.

ISP

Presentational components receive only the props they render. They do not receive entire stores or query clients.

DIP

Features depend on typed API abstractions and view models. UI does not depend directly on fetch, storage, or server internals.

Tenant safety

Every route, query key, mutation, stream, and persisted selection carries tenant identity explicitly.
